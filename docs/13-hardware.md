# 硬體選型：本地跑模型值得嗎，32GB 還是 128GB

> **難度**：中階　|　**前置**：[核心路徑第 2 節](../README.md#2-兩種連線模式先搞懂差別)、[成本控制](05-cost.md)
> 三個反直覺的結論：頻寬比容量重要、MoE 讓「大模型」和「慢」脫鉤、最貴的 dense 模型反而最不划算

[← 部署上線](12-deployment.md)　·　[全部進階主題](README.md)　·　[回到核心路徑 →](../README.md)

> ⚠️ **先說清楚這篇的性質。**
> 這篇的模型佔用與速度是**依規格推算的估計值，不是實測**——我沒有 Apple Silicon 機器可以跑。
> 規格數字（記憶體、頻寬、模型參數）都有官方來源，但推導出來的 tok/s 是理論上限，實測普遍只有四到七成。
> 本 repo 其他篇的數字都是實跑出來的，這篇不是，所以特別標出來。

## 1. 這篇要回答什麼

整份教材一路是雲端優先的。但沿路我們也實測記錄了 Ollama Cloud 的五個限制：

| 限制 | 出處 |
| --- | --- |
| 沒有 embedding，向量 RAG 做不了 | [RAG](06-rag.md) |
| `format` 結構化輸出不生效 | [結構化輸出](01-structured-output.md) |
| 免費方案只有三個模型可用 | [核心路徑第 4 節](../README.md#4-環境準備) |
| 偶發 500，多輪 Agent 撞上機率高 | [框架與可觀測性](08-frameworks-observability.md) |
| 按 GPU 時間計費，配額有限 | [成本控制](05-cost.md) |

前四個在本地都不存在。所以問題就變成：**買一台跑得動大模型的機器，值得嗎？如果值得，該買多大？**

## 2. 最重要的一件事：32GB 和 128GB 不是同一顆晶片

這是選型時最容易被忽略的：

| | 32GB | 128GB |
| --- | --- | --- |
| 晶片 | **M5 Pro** | **M5 Max**（40 核 GPU） |
| 記憶體頻寬 | **307 GB/s** | **614 GB/s** |
| 可選記憶體 | 16 / 24 / 32 / 64 GB | 36 / 48 / 64 / 128 GB |

M5 Max 的記憶體選項**根本沒有 32GB**。所以「選 32GB」等於「選 M5 Pro」，而 M5 Pro 的頻寬只有一半。

**為什麼頻寬是關鍵**：產生每一個 token，都要把模型權重從記憶體讀進計算單元一次。所以

```
token/s 的理論上限 ≈ 記憶體頻寬 ÷ 每個 token 要讀取的權重量
```

容量決定**塞不塞得下**，頻寬決定**跑得多快**。而這兩台的頻寬正好差兩倍——**即使是兩台都跑得動的模型，128GB 也快一倍**。這不是「買保險以防哪天要跑大模型」，是日常每一次推論都有感。

## 3. 實際跑得動什麼

GPU 可用記憶體大約是統一記憶體的 75%（macOS 預設，`sysctl iogpu.wired_limit_mb` 可調高）：32GB → 約 24GB，128GB → 約 96GB。

| 模型 | 量化 | 佔用 | 32GB | 128GB | 32GB tok/s | 128GB tok/s |
| --- | --- | --- | --- | --- | --- | --- |
| `qwen3.5:9b` | Q4 | 6 GB | ✅ | ✅ | ~56 | ~112 |
| `gemma4:12b` | Q4 | 8 GB | ✅ | ✅ | ~41 | ~82 |
| `qwen3.5:27b` | Q4 | 17 GB | ✅ | ✅ | ~18 | ~36 |
| `gemma4:31b` | Q4 | 19 GB | ✅ | ✅ | ~16 | ~32 |
| `70B 級` | Q4 | 40 GB | ❌ | ✅ | — | ~15 |
| `gpt-oss:120b` | MXFP4 | 61 GB | ❌ | ✅ | — | **~123** |

（tok/s 為理論上限，實測約四到七成）

## 4. 反直覺之一：MoE 讓「大模型」和「慢」脫鉤

看上表最後兩列。`70B` 佔 40GB 卻只有 ~15 tok/s，而 `gpt-oss:120b` 佔 61GB —— 更大 —— 卻有 ~123 tok/s。**大了 50%，快了八倍。**

原因是架構不同：

| | dense（如 70B） | MoE（如 gpt-oss:120b） |
| --- | --- | --- |
| 總參數 | 70B | 116.8B |
| **每個 token 實際啟用** | **全部 70B** | **只有 5.1B** |
| 佔記憶體 | 40 GB | 61 GB |
| 每 token 讀取 | 40 GB | **約 5 GB** |

MoE（Mixture of Experts）把前饋層拆成 128 個「專家」，每個 token 只路由到其中 4 個。**權重全都要放在記憶體裡，但每次只讀取一小部分。**

所以：

- **容量看總參數**（要塞得下 61GB）
- **速度看啟用參數**（每 token 只讀 5GB）

> **我一開始算錯了這件事。** 先前我估「120B 在 128GB 上約 8 tok/s，比雲端慢一個數量級」，那是把它當 dense 模型算的（61GB ÷ 614GB/s）。對 MoE 而言太悲觀了一個數量級。這個更正很重要，因為它直接改變結論：**本地跑 gpt-oss:120b 是實用的，不是勉強能動。**

實務含意：**挑本地模型時優先看 MoE**。同樣的記憶體預算，MoE 給你更強的能力和更快的速度。

## 5. 反直覺之二：70B dense 是最不划算的一格

它是唯一「只有 128GB 跑得動、但跑起來又慢到痛苦」的選項。~15 tok/s 意味著一段兩百字的回答要等十幾秒——而 Agent 一個任務要跑好幾輪。

所以如果你買 128GB 的理由是「想跑 70B」，**理由是錯的**。真正的理由應該是 MoE 模型。

## 6. 別忘了 KV cache

模型權重只是一部分。對話越長，KV cache 越大，而 Agent 的 context 是一路累積的（見[多輪對話與 Context 管理](09-memory-context.md)）。

```
KV cache 每 token 位元組 = 2 × layers × kv_heads × head_dim × bytes_per_element
```

以一個 36 層、8 個 KV head、head_dim 64 的 GQA 模型、fp16 為例（實際數字請查你的模型 `config.json`）：

| Context | KV cache |
| --- | --- |
| 8K | 0.6 GB |
| 32K | 2.4 GB |
| 128K | **9.7 GB** |

這對 32GB 影響很大。`gemma4:31b` 佔 19GB，可用約 24GB，只剩 5GB 給 KV cache——**32K context 就快滿了**。

所以 32GB 的實務舒適區其實是 **14B 以下**，而不是表上寫的 31B 跑得動。表格只告訴你「載入得了」，沒告訴你「還能不能好好對話」。

## 7. 本地才有的能力

這些不是「雲端比較不方便」，是**雲端根本做不到**：

| 能力 | 說明 |
| --- | --- |
| **完整的 RAG 工具鏈** | embedding + reranker + 生成模型同時常駐。以 120b(61GB) + embedding(0.6GB) + reranker(1.2GB) 估算約 63GB，128GB 綽綽有餘。[雲端沒有 embedding](06-rag.md)，這個形態只有本地做得到 |
| **Modelfile 自訂** | 把系統提示、`temperature`、`num_ctx` 烘進模型，團隊共用一個行為一致的 `ourteam-agent:latest` |
| **微調 / LoRA** | 用你的工單、你的程式碼風格訓 adapter。雲端完全沒有這條路，而且**訓練的記憶體需求遠高於推論**——這是 128GB 相對 32GB 最實在的差距 |
| **存取模型內部** | hidden states、logits 分布做信心度估計、constrained decoding。雲端只給你最終文字 |
| **`format` 真的有效** | [結構化輸出那篇](01-structured-output.md)的坑在本地不存在 |
| **沒有 rate limit** | 要跑一萬份文件的批次評估？開著讓它跑就好 |
| **版本確定性** | 雲端模型會被更新或下架，你的[評估基準線](06-rag.md#9-怎麼自動驗證-rag-的正確率)會無聲飄移。本地的那一版永遠是那一版 |
| **離線** | 飛機上、客戶內網、斷網 demo |

## 8. 誠實的代價

**大模型在雲端還是比較快。** 實測雲端 `gpt-oss:120b` 約 100 tokens / 1.1s（≈90 tok/s，且這是實測不是估算）。本地 128GB 的理論上限 ~123 tok/s，打對折後大約在同一個量級——**接近，但雲端仍占優**，而且雲端不用先花錢買機器。

另外兩件事：

- **筆電會發熱降頻**。持續跑推論時實際速度會低於短測。
- **32GB 不是「小一號」，是不同的天花板**。它跑不了任何 MoE 大模型，這條路整個被封住。

## 9. 決策建議

**如果雲端會一直是主力生成**（也就是這份教材的預設架構），**32GB 完全夠用**：

| 用途 | 32GB |
| --- | --- |
| RAG 的 embedding（0.6GB） | ✅ 綽綽有餘 |
| 本地跑路由／分類小模型（[成本控制](05-cost.md)） | ✅ 夠 |
| 開發、跑這份教材 | ✅ 完全夠 |
| 離線跑 30B 級 | ⚠️ 載得動，但 context 會很緊 |
| 離線跑 MoE 大模型 | ❌ 做不到 |
| LoRA 微調 | ❌ 記憶體不足 |

**128GB 值得的兩個理由**（而且只有這兩個）：

1. **你要「完全不依賴雲端」的能力。** 128GB + MoE 模型是唯一能一次拿掉第 1 節那五個限制、而且速度堪用的選項。
2. **你要做微調。** 這是雲端沒有的路，而 32GB 做不了有意義的訓練。

如果理由是「以防萬一想跑大模型」——**那不夠**。真正該說服你的是**頻寬差兩倍**（日常每次都有感）加上 **MoE 讓 120b 變得實用**。

## 10. 最務實的架構：兩邊都用

跟[混合式 RAG](06-rag.md) 是同一個思路，只是放大到整個工作流：

```
本地                              Ollama Cloud
├─ embedding（毫秒級、量大）        ├─ 互動式大模型推理（要快）
├─ reranker                       └─ 需要最強能力的規劃步驟
├─ 路由／分類小模型
├─ 批次評估（不佔雲端配額）
├─ 微調實驗
└─ 敏感語料
```

判準很簡單：

> **量大、要離線、要改模型 → 本地**
> **單次要快、要最強能力 → 雲端**
